# Feature request: one-time upload URLs (out-of-band file transfer)

**Status:** proposed · **Type:** feature + bug fix · **Affects:** REST API (`app/`), MCP wrapper (separate repo), `AGENT.md`

## Summary

Agents currently upload files through the MCP tools by pasting the file
contents into tool-call arguments (`write_file`, or `begin_write` →
`write_chunk`* → `commit_write`). For anything over about 1 KB this is slow
(it takes minutes) and unreliable (SHA-256 mismatches at `commit_write`, and
malformed files).

Add a flow where the agent names a local file and a remote path, gets back a
**one-time upload URL**, sends the bytes with `curl` from its own shell, and
polls an **upload ID** for the result. File bytes should never pass through
the model.

## Problem

### What happens today

1. The agent reads a local file.
2. The model writes that content back out, token by token, as a JSON string
   argument. For binary files it writes base64 and has to split it on
   4-character boundaries. For text it has to avoid splitting multi-byte
   characters.
3. For large files the model also splits the content into chunks and tracks
   `seq` numbers.
4. `commit_write` requires `expect_bytes` / `expect_sha256`, which the model
   has to supply.

### Why it fails

- **Slow:** every byte costs output tokens. A few KB of base64 is thousands
  of tokens across several round trips.
- **Corrupt data:** a model re-typing thousands of characters of base64 or
  dense text will drop, duplicate, or change a few of them. The SHA check
  catches this, so the "SHA mismatch" errors come from corruption during the
  copy, not from the check itself.
- **Invented hashes:** an agent without a shell can't compute SHA-256, so it
  guesses `expect_sha256`, and the guess fails.
- **Bookkeeping errors:** chunk boundaries, `seq` ordering, base64 padding
  sealing the stream, and so on. The model has to get all of this right, and
  a mistake produces a refusal or a malformed file.

No change to the chunking rules fixes this. The design is wrong because it
uses the model as the transport.

### Constraint

A remote MCP server can't read the agent's filesystem, and the agent's
sandbox usually can't accept inbound connections, so the server can't fetch
the file. **The agent has to push the bytes over HTTP itself.** This feature
lets it do that safely and without handing the long-lived bearer token to
the sandbox.

## Proposed design

### Flow

```
agent ──MCP request_upload(path)──▶ MCP wrapper ──POST /v1/uploads──▶ API
      ◀── {upload_id, upload_url, curl_command, expires_at} ──────────────┘

agent shell:  curl -sS --fail -T ./local/file "<upload_url>"      (bytes go direct)

agent ──MCP upload_status(upload_id)──▶ ... GET /v1/uploads/{id}
      ◀── {state: "complete", size, sha256, path}

agent shell:  sha256sum ./local/file    → compare with the returned sha256
```

### REST API (this repo, `app/main.py`)

#### `POST /v1/uploads` — create an upload ticket (requires the rw bearer token)

Request body:

```json
{
  "path": "reports/q3/data.parquet",
  "overwrite": true,
  "parents": true,
  "max_bytes": 52428800,
  "expect_sha256": null
}
```

| Field | Notes |
|---|---|
| `path` | Validated **now** with `VAULT.components()`. Reject traversal, denied names, and similar here so the agent gets the error before it uploads anything. |
| `overwrite` | Default `true`. If `false`, return `409` now if the file exists. The atomic write checks again at upload time. |
| `parents` | Default `true`, to match the MCP `write_file` default. |
| `max_bytes` | Optional. Clamp to `CONFIG.max_upload_bytes`. |
| `expect_sha256` | Optional. If set, the upload is rejected and nothing is written unless the hash matches. It is **not required**. The agent verifies afterwards with `upload_status` instead. |

Response `201`:

```json
{
  "upload_id": "u_3f9c…",
  "upload_url": "https://claude-files.guthrieec.dev/v1/uploads/u_3f9c…/<secret>",
  "method": "PUT",
  "expires_at": 1790000000.0,
  "max_bytes": 52428800,
  "curl_command": "curl -sS --fail -T <LOCAL_FILE> 'https://…/v1/uploads/u_3f9c…/<secret>'"
}
```

#### `PUT /v1/uploads/{upload_id}/{secret}` — upload the bytes (no bearer token)

- The secret in the URL path is the only authorization. Compare it with
  `hmac.compare_digest` against a value generated by `secrets.token_urlsafe(32)`.
  Put it in the **path, not the query string**, so it's less likely to end
  up in logs.
- Single use: the ticket moves `pending → receiving → complete | failed`. A
  second `PUT` on a ticket that isn't `pending` gets `409`. An expired
  ticket gets `410`.
- Stream the body through the existing `_write_body()` / `VAULT.atomic_write()`
  path, with the ticket's `overwrite` / `parents` / `max_bytes`. Hash the
  bytes as they stream in with `hashlib.sha256()`. Don't re-read the file.
- If the ticket has `expect_sha256` and the hash doesn't match, raise inside
  the `atomic_write` block **before** `committer.commit(fd)` so the temp file
  is removed and the target is left untouched. Mark the ticket `failed` with
  `code: "sha_mismatch"`.
- Response: `{"ok": true, "upload_id": …, "path": …, "size": …, "sha256": …}`.
  `curl` output alone is then enough to confirm the upload, and
  `upload_status` is just a backup.
- The per-minute rate limit still applies (`_rate_limit()`).
- Also accept `POST` for clients that can't easily send a `PUT`.

#### `GET /v1/uploads/{upload_id}` — status (requires the bearer token; ro or rw)

```json
{
  "upload_id": "u_3f9c…",
  "path": "reports/q3/data.parquet",
  "state": "pending | receiving | complete | failed | expired",
  "bytes_received": 1048576,
  "size": 52428800,
  "sha256": "…",
  "error": {"code": "…", "message": "…"},
  "created_at": 0.0, "expires_at": 0.0, "completed_at": 0.0
}
```

`bytes_received` updates while the upload streams, so long uploads can
report progress.

#### Ticket storage

- The container runs a single uvicorn worker (see `Dockerfile` `CMD`), so an
  in-process dict guarded by a lock is fine. Add a comment saying this
  depends on the single worker.
- The container runs `--read-only` with a small `/tmp` tmpfs, and tickets
  are short-lived, so **don't** persist them. Losing them on restart is
  acceptable. The agent sees `404` and requests a new ticket.
- Delete expired and finished tickets when new tickets are created, and cap
  the number of live tickets (for example 100) so they can't use unbounded
  memory.
- `sweep_temp_files()` already removes stray `.upload-*.tmp` files at
  startup. No change is needed.

#### Config (`app/config.py`)

| Env var | Default | Purpose |
|---|---|---|
| `UPLOAD_TICKET_TTL_SECONDS` | `900` | How long a ticket remains valid if unused |
| `UPLOAD_TICKETS_MAX` | `100` | Maximum number of live tickets |
| `PUBLIC_BASE_URL` | *(unset)* | Used to build `upload_url`. If unset, derive it from the request (`--proxy-headers` is already on, so `X-Forwarded-Proto/Host` from cloudflared work). |

Report the TTL and the ticket cap in `GET /v1/info`.

### MCP wrapper (separate repo, not in this checkout)

The MCP server that provides `get_folder_info`, `write_file`, `begin_write`,
`write_chunk`, `commit_write`, and so on isn't in this repository. The
implementer needs its source. Changes there:

1. **Add `request_upload(path, overwrite=true, parents=true, expect_sha256=null)`.**
   It calls `POST /v1/uploads` and returns the ticket, including a ready-made
   `curl_command`. Tool description (important, because this is what agents
   read):
   > Use this for any existing local file, of any size or type. Run the
   > returned `curl_command` from your shell with the local path filled in.
   > The bytes go directly over HTTP and never pass through tool arguments.
   > Then compare `sha256sum <file>` with the `sha256` in the curl response
   > or in `upload_status`.
2. **Add `upload_status(upload_id)`.** It wraps `GET /v1/uploads/{id}`.
3. **Change the other write tools' descriptions:**
   - `write_file`: "For content you are *writing now* (a short report,
     generated text). If the content already exists as a local file, use
     `request_upload` instead."
   - `begin_write` / `write_chunk` / `commit_write`: mark them as a
     **last resort for agents with no shell or no outbound network access**.
     Consider deprecating them.
4. **Make hashes optional in `write_file`.** Stop *requiring*
   `expect_bytes`/`expect_sha256`, and **return** the server-computed
   `size` and `sha256` in the result. An agent that has a shell can verify
   afterwards. An agent without one can't produce a real hash, so requiring
   one only causes failures. Keep `expect_*` as optional inputs.
5. **Mention the preferred path in `get_folder_info`.** Its output should
   say that `request_upload` is the preferred way to upload files.

### Docs

- `AGENT.md`: add an "Uploading an existing file" section at the top of the
  write guidance that shows the three-step flow (request, curl, verify).
  Also note that agents with a shell and the bearer token can already
  `curl --data-binary @file -X PUT …/v1/content/<path>?parents=true`.
- `README.md`: add the three new endpoints to the API table and the new env
  vars to the config section.

## Security considerations

This adds a write endpoint that doesn't use the bearer token, so each point
below needs a test:

- **Scope:** a ticket can write exactly one path, once. Validate the path at
  ticket creation, then run it through the full `Vault` path again at write
  time. A symlink planted between issuing the ticket and the upload must
  still be refused by `atomic_write`.
- **Secret handling:** ≥256 bits of entropy, constant-time comparison, kept
  out of logs. The access log line should print the path without the secret.
  uvicorn's access log prints request paths, so either redact them or log
  the ticket ID only. It is never accepted as a bearer token and is never
  valid for other endpoints.
- **Expiry and single use:** enforced on the server. A used, failed, or
  expired ticket can't be reused.
- **Size:** enforce `max_bytes` while streaming, not just from
  `Content-Length`.
- **Read-only tokens can't create tickets** (`require_write`).
- **Guessing:** a bad `upload_id` or secret returns `404`, identical in both
  cases, and is logged like other denials.

## Acceptance criteria

- [ ] An agent in a shell can upload a 50 MB binary file with **one**
      `request_upload` call, **one** `curl`, and **zero** file bytes in tool
      arguments, and the returned `sha256` matches `sha256sum` of the local
      file.
- [ ] `upload_status` shows `bytes_received` increasing while a large upload
      streams, then `complete`.
- [ ] Reusing a ticket → `409`. Expired ticket → `410`. Wrong secret →
      `404`. Read-only token creating a ticket → `403`.
- [ ] `expect_sha256` mismatch → nothing at the destination, no `.upload-*.tmp`
      left behind, ticket `failed` with `sha_mismatch`.
- [ ] `overwrite=false` onto an existing file → `409` at ticket creation.
- [ ] Every containment test in `tests/escape_suite.py` still passes in both
      configurations of `tests/run_tests.sh`, and new escape tests cover
      tickets:
  - [ ] a ticket for `../outside.txt`, `/etc/x`, `.git/config`, or a symlinked
        parent is refused at creation;
  - [ ] a symlink planted at the target *after* the ticket is issued makes
        the upload fail and leaves the canary file outside unchanged;
  - [ ] the secret doesn't appear in container logs.
- [ ] MCP `write_file` no longer requires hashes and returns `size` + `sha256`.
- [ ] `AGENT.md`, `README.md`, and the MCP tool descriptions point agents to
      `request_upload` for existing files.

## Out of scope

- A server-side fetch-from-URL (pull) mode. Agent sandboxes usually aren't
  reachable from outside, and it would turn the server into an SSRF vector.
- Resumable or multi-part uploads. One streamed `PUT` of up to 256 MiB is
  enough here. Revisit only if uploads start failing mid-transfer through
  cloudflared.
- Agents with no shell or no outbound network access. They can't use this
  flow at all. For them, the fix is item 4 in the MCP list: stop requiring
  hashes they can't compute.
